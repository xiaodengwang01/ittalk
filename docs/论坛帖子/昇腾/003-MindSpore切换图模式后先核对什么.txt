MindSpore 动态图能跑，切到图模式后先核对什么

网络在 PyNative 模式下能运行，切到 Graph 模式后报错，最容易着急改的是模型结构。但两种模式执行代码的方式不同，先把问题缩小到一段计算，往往更容易找到差别。

PyNative 更方便按 Python 的执行过程观察中间变量，逐个检查算子；Graph 会涉及图编译与优化，对代码表达方式也有相应要求。动态图通过，说明当前执行路径走通了，还不能替代对图模式的验证。反过来，图模式报错也不等于网络计算思路一定有问题。

排查时可以先留一份很小的固定输入，固定权重和模型的训练或推理状态。先看两边是否都能完成，再对照输出的形状、类型和数值。随机输入、随机初始化以及训练状态都在变时，很难知道差异来自模式还是来自测试条件。

若连编译都没有通过，就沿报错位置查看 Python 语法、对象类型和控制流是否符合当前版本的图模式支持范围。不要直接照搬“图模式不能写某种语句”的旧结论；框架的支持范围会变化，应该查自己使用的版本，并把相关代码裁成最小片段确认。

如果能运行但结果不一致，可以在计算的几个边界分别比较中间结果。先找到第一次偏离的位置，再检查其输入。最后一层出现错误，可能只是把前面的问题放大了；一开始就替换最后一个算子，未必能缩小范围。

调试输出本身也需要注意。PyNative 支持更直接地观察执行过程，但设备算子仍可能异步执行，报错显示的位置未必就是出错任务的下发位置。MindSpore 文档提供了由异步切换为同步的调试思路，这属于定位手段；调试设置保留下来测性能，结果就可能和正常运行不同。

两种模式的性能对比另开一组记录更清楚。把首次编译耗时和重复执行耗时分开，使用相同输入，并写清数据准备是否计入。Graph 可以利用图优化，但具体网络是否受益、收益有多大，仍要由实际负载回答。

对刚开始接触 MindSpore 的人，一次练习可以只做到这里：保留一个能稳定复现差异的小例子，写出两种模式各走到哪里，以及第一处不一致是什么。这样的记录比“动态图正常，图模式不行”更方便继续讨论，也不需要一开始就贴整套工程。

本文依据 MindSpore《PyNative 模式应用》和《报错分析》的调试策略整理，未声称在某个版本上完成复现。具体语法、调试接口与默认模式，以所使用版本的文档为准。
