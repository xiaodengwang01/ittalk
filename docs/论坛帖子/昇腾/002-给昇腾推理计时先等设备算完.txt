给昇腾推理计时，先确认设备真的算完了

同一段推理代码，只在前后记录 Python 时间，测出来的耗时很短；把结果取回 CPU，时间却突然长了一截。这种差别不一定来自模型本身，也可能是两次计时等到了不同的位置。

在 TorchNPU 的异步执行过程中，CPU 把任务交给设备后，可以继续往下运行。Python 函数返回，不等于 NPU 上的计算已经结束。若结束时间记在任务刚下发之后，测到的就可能主要是下发开销。

先写清楚这次要测什么。只关心输入已经在设备上的模型执行，就不要把文件读取和输入准备混进来；关心用户从发送请求到拿到结果要等多久，就应该保留预处理、传输、排队和后处理。两种口径都可以有用，但不能拿一个去代表另一个。

测一段相对独立的设备计算时，一个容易核对的做法是：先完成预热，在计时开始前等待先前任务结束；执行待测计算后，再等待目标设备上的任务完成，最后读取结束时间。TorchNPU 提供了 synchronize 同步接口，具体调用入口以安装版本为准。

前面的等待是为了不把上一轮遗留任务算进来，后面的等待是为了不漏掉本轮还没执行完的任务。只补后面的同步，仍可能把之前排队的工作一起记到这一轮。

同步也会改变执行方式。如果原程序依靠多条流或者多个请求重叠工作，给每一步都加同步，测到的是被人为串行化后的表现。单次执行耗时和持续处理请求的吞吐，需要分别设计测试，不能用同一套同步方式含糊带过。

还有两种时间值得单独留下：第一次执行，以及预热后的稳定执行。首次运行可能包含初始化、编译或缓存建立。若业务很在意冷启动，第一轮就应保留；若比较稳定吞吐，则应说明预热条件，而不是直接把最快的一轮当成绩。

重复测试时尽量固定输入形状、数据类型、模型模式和设备上的其他负载。记录若干轮的中位数与波动，比只有一个小数更容易判断差异。把结果转回 CPU、打印张量、保存文件等动作，也要明确是否属于计时范围。

如果某次修改让耗时下降，先确认输出正确，再用相同口径复测。否则，输入已经在 NPU 上的结果和每次都重新传输输入的结果，放在一起只会产生一个看似很大的“加速”。

这篇整理的是计时方法，没有提供设备实测数字。参考资料为 TorchNPU《适配简介》及同步 API 清单、PyTorch《PyTorch Benchmark》。PyTorch 教程中的 CUDA 示例用于理解计时原则，不能直接当作 NPU 接口照搬。
