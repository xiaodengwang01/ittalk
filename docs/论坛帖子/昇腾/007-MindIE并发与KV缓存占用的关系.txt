MindIE 单请求能跑，增加并发后为什么先碰到显存

模型权重已经装进 NPU，单个请求也能正常回答，增加并发后却开始出现显存压力。这时只计算“模型文件有多大”，通常还少算了请求执行时需要的空间。

对于采用 KV Cache 的自回归推理，模型会保存先前 token 对应的 Key 和 Value，供后续生成使用。请求还在继续，缓存也要继续服务这段上下文。它与模型权重的生命周期不同，不能仅按权重占用来判断还可以接多少请求。

理解这一点，可以先看两个方向。在模型与缓存精度等条件固定时，序列更长，通常需要保存更多缓存；同时活动的序列更多，也会增加缓存需求。因此，单请求短文本成功，并不能证明多个长请求也有足够空间。

MindIE 的相关性能文档用 Block 来描述 KV Cache 分配。观察时要分清总共有多少可用块、当前使用了多少，以及请求的上下文需要多少。Block 大小和分配策略有版本差异，不能把某篇文章里的默认值当成所有环境的容量常数。

并发数本身也有不同口径。客户端同时发出多少请求、服务里有多少请求在等待、当前正在处理多少条序列，并不必然相等。排队请求增加，和活动序列占用的缓存增加，需要结合调度状态判断。

再看输入与输出长度。若只固定输入，却允许生成长度明显变化，不同轮次的缓存压力就可能不同。仅记最大输出限制还不够，实际生成长度、停止条件以及是否启用了前缀复用等策略，也会改变比较的前提。

用容量公式做估算时，注意模型的注意力结构。普通多头注意力与采用较少 KV 头的结构，缓存量不能直接套同一个头数。并行切分方式、缓存的数据类型，以及运行时其他空间，也都会影响每张卡的实际可用容量。没有这些信息时，给出一个“这张卡能支持多少并发”的固定答案并不可靠。

排查可以先固定一组输入与输出长度，逐级增加请求压力，同时记录缓存使用率、活动请求数和错误。若显存仍有余量，但首 token 等待已经明显恶化，就不能只按显存上限继续加并发。容量和时延要求需要一起满足。

这篇整理的是判断顺序，未测量具体卡型的并发上限。参考资料：MindStudio《显存瓶颈分析案例》、MindIE《服务化参数配置》及《服务管理及控制指标查询接口》。
