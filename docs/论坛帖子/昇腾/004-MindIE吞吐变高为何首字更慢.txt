MindIE 吞吐变高，为什么等第一个字反而更久

一组推理测试显示每秒输出的 token 更多，实际使用时却感觉回答开始得更慢。这两个结果可以同时成立，因为它们衡量的不是同一件事。

TTFT 关注首个 token 的等待时间，TPOT 通常关注首个 token 之后，平均每个输出 token 的耗时。输出 token 吞吐则描述测试窗口内，服务整体每秒产出了多少输出 token。单个请求的体验和整套服务处理工作量的能力，需要放在一起看。

先看统计发生在哪里。客户端记录的首 token 时间，可能包含网络、排队、分词和服务端计算；服务内部的指标可能只覆盖其中一段。例如 MindIE 3.0.0 的管控指标文档明确说明，其相应 TTFT 指标不包含 HTTP 通信、分词以及 P/D 分离的 KV 传输时间。把这个值和客户端端到端测量直接比较，会把统计范围的差异误读成性能变化。

再看负载有没有变化。短提示词、短回答，和长提示词、长回答，即使并发数相同，也不是同一组工作。提示词长度会影响预填充阶段，输出长度会改变后续生成的工作量。最大输出长度只是限制，真正生成了多少 token 也要记录。

假设两个测试都写着“并发 8”，一个主要生成很短的答案，另一个持续输出长文本，只比较请求数每秒，就很难说明模型执行能力。请求吞吐、输出 token 吞吐和长度分布至少要能对上，才有继续比较的基础。这里的数字只是说明口径，不是某台设备的测试结果。

并发增加时，服务有机会更充分地利用批处理，但请求也可能需要等待。总吞吐上升，不保证每个请求更早开始输出。若目标是交互式问答，就应同时看首 token 的中位数和较慢部分的分位值，而不是只追求一条漂亮的吞吐曲线。

TPOT 也不能覆盖所有停顿感受。一个请求的平均生成速度尚可，中途仍可能有较长间隔。分析流式输出时，若工具提供逐 token 间隔或相应分布，可以结合查看；先确认该工具的定义，再比较不同报告中的名称。

读完一份报告，比较有用的结论是“在这组输入和输出长度下，某个并发设置满足了等待时间要求，并带来了多少吞吐”。“每秒 token 越高越好”省略了用户能否接受等待这一层条件。
