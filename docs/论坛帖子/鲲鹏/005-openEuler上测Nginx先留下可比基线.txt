在 openEuler 上测 Nginx，第一份基线应该记什么

Nginx 已经启动，压测工具也输出了一行 Requests/sec，第一次测试很容易就到此结束。可等到修改参数以后，如果不知道上一轮到底测了什么，这个数字很难再用来比较。

先固定请求内容

静态小文件、较大的文件、反向代理和真实业务接口，背后的工作不同。基线应写清请求路径对应的内容、响应大小、是否启用 TLS，以及有没有经过代理和后端。测试一个固定静态文件，得到的是这条访问路径的表现，不能直接代表完整业务。

使用 wrk 时，线程数和连接数也要分开。线程数描述压测工具用多少线程工作，连接数描述维持多少 HTTP 连接。它们都不是服务端工作进程数，也不能仅凭连接数就推算每秒会产生多少请求。

再确定压测从哪里发出。同机测试会让客户端与服务端争用资源；跨机测试则会引入网络链路和另一台机器的能力。两种方式都可以用于特定目的，但切换测试位置以后，应重新说明比较条件。

除了吞吐，还留下什么

至少保留延迟分布、错误与超时情况，以及响应是否符合预期。wrk 的延迟统计选项可以提供更详细的分布信息。一个更高的吞吐值，如果伴随大量失败请求，不能直接写成业务处理能力提升。

服务端与客户端都需要观察。服务端还没有明显压力，可能是负载太轻，也可能是压测端的 CPU、端口或网络先达到限制。先验证请求确实到达了预期服务，再决定是不是应该修改 Nginx 配置。

初次建立基线时，固定测试时长并重复几轮，把预热和正式测量分开说明。涉及文件读取时，缓存状态也可能改变结果。只保留最快的一轮，会隐藏环境波动；几轮结果差得很远时，应先解释波动来源。

此后每次只改一项需要验证的配置，并保留原值。比如调整工作进程相关设置时，其他请求内容与压测条件保持一致，才容易判断变化是否符合预期。没有稳定基线，一次改很多参数，最后往往只能知道“好像快了”。

这份记录不需要写得复杂：软件与系统版本、请求内容、客户端位置、线程和连接设置、测试时长、吞吐、延迟及错误，已经足够支撑下一轮对照。

参考资料：wrk 官方 README 的选项与压测说明。本文为适用于 openEuler 上 Nginx 测试的记录方法，未运行压测，也不提供可跨服务器照抄的性能数字。
