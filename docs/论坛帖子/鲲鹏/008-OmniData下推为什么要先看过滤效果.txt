读 OmniData 算子下推，先看能少传多少数据

Spark 查询慢，开启算子下推以后是否就会变快？先把数据经过哪些地方讲清楚，这个问题才容易判断。

在相关存算分离场景里，计算节点需要从存储侧读取数据，再做过滤或聚合。OmniData 可以把支持的部分计算放到靠近数据的位置执行，让处理后的结果再传回计算侧。收益的一部分来自少传数据，也来自两侧计算资源的重新分配。

过滤效果是一个直观的观察点。假设读取一百万行，过滤以后只剩一万行，先过滤再传输，就有机会大幅减少传输的行数；若最后还剩九十多万行，能省下的部分就小得多。这里是说明原理的假设数字，不是实际测试，也不能直接用行数比例预测字节数或总耗时。

这也是为什么统计信息值得核对。优化器需要估计过滤效果，数据分布变了而统计没有跟上，判断依据就可能失真。看到“没有下推”，应结合日志与执行计划查看原因，不要只为了让开关生效就把判断阈值全部放宽。

另外还要看能否下推。引擎版本、插件能力、表达式和数据类型，都会影响支持范围。普通文件读取中的过滤优化与 OmniData 的下推也不能只凭名字混为一谈，应确认实际走到了什么执行路径。

即便支持，下推也不是把计算开销消掉了。若存储侧已经很忙，把更多聚合工作继续放过去，可能增加那一侧的等待。鲲鹏官方的 OmniRuntime 文章就提醒过：计算侧资源充裕、数据源压力较大时，部分下推反而可能拖慢整体执行。

验证时可以保留一组固定 SQL、数据快照与资源条件，对照启用和未启用相关下推时的执行过程。除了总耗时，还看实际传输量、两侧 CPU 与 I/O，以及结果是否一致。缓存状态不同，也会影响前后两次的可比性。

如果总耗时降低，但存储侧负载明显提高，下一步还需要观察多个查询同时运行时的表现。单条 SQL 获益，不代表共享这批资源的其他作业也都获益。调优结论最好写清数据规模、并发场景和瓶颈所在。

参考资料：鲲鹏官方《如何使用 OmniRuntime 算子下推提升大数据引擎计算性能》、徐立《基于 Apache Hive 实现的近数据计算，提升计算性能的特性——OmniData》。本文为原理与验证思路整理，没有运行 Spark 或 OmniData 测试。
