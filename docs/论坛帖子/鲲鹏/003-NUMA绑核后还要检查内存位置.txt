NUMA 绑核以后，还要看内存留在了哪里

给进程指定了 CPU，性能却没有改善，甚至更慢，不能只检查绑核命令有没有生效。CPU 在哪里执行，以及它频繁读取的内存在哪里，是两个需要分别确认的问题。

在 NUMA 系统中，不同节点的处理器与内存之间有不同的访问路径。把计算放到一个节点，并不自动意味着已有数据也一起搬了过去。如果线程仍然大量访问别的节点上的数据，预期中的本地访问优势就未必出现。

先认识当前机器，再决定怎么绑定。lscpu 和 numactl 的硬件信息可以帮助查看 CPU 与 NUMA 节点的关系。物理服务器、虚拟机以及不同配置的实例，暴露出来的拓扑可能不同；“都是鲲鹏”不足以推导出相同的节点数和 CPU 编号分布。

内存什么时候分配也很重要。Linux 的 NUMA 内存策略主要影响相应策略下的新分配，已有页面不会因为后来改了策略就必然自动搬家。因此，一个先初始化大量数据、再改亲和性的测试，与从启动开始就按相同策略分配的测试，前提可能不同。

观察进程的页分布，有助于发现数据主要落在哪些节点，但页分布仍不等于访问流量。某个节点上放着较多页面，不代表这些页面就是当前最频繁读取的部分。要判断远端访问是否影响性能，还要结合负载行为与性能采样。

绑得越集中也不一定越好。若线程很多、内存需求大，只给一个节点可能压缩可用核心和内存带宽。原来跨节点运行虽然有代价，却可能用到了更多资源。比较时既要看访问距离，也要看绑定之后是否增加了竞争。

一个便于解释的对照，是保持线程数、数据规模和输入内容一致，分别记录默认策略与明确亲和策略下的实际放置和业务耗时。不要同时更改线程数、页大小和编译选项，否则即使结果改善，也难以说明是哪项调整起了作用。

如果最终没有收益，也可以留下明确结论：当前负载的主要时间可能不在跨节点访存，或者集中绑定造成了新的限制。下一步应该由采样数据决定，而不是继续缩小 CPU 范围碰碰运气。

本文依据鲲鹏《CPU 亲和性》相关编程指南和 Linux《NUMA Memory Policy》整理。未对具体鲲鹏机型进行绑核测试，也未给出可直接套用的 CPU 编号。
