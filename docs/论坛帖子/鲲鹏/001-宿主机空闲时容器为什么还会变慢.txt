宿主机 CPU 还有空闲，鲲鹏容器为什么仍可能变慢

看到宿主机 CPU 利用率不高，就把 CPU 从排查清单里划掉，可能会漏掉容器自己的配额限制。整机还有多少空闲资源，和某个容器此刻还能使用多少 CPU 时间，并不是同一个问题。

鲲鹏九月精选里，wws2437576178 的《宿主机空闲，鲲鹏容器照样限速》专门做了这组对照。读这个案例时，值得留意的不只是最后的性能变化，还有作者怎么排除了第一轮数据中的干扰。

先把配额的含义弄清楚

容器的 CPU 配额可以理解为一段周期内允许消耗的 CPU 时间。用一个简化例子说明：周期设为 100000 微秒，配额设为 50000 微秒，名义额度就是 0.5 个 CPU。

这不是把容器固定在某个核上，也不是允许它使用整台机器一半的算力。额度由组内任务共享；多个线程并行运行时，会共同消耗这份 CPU 时间。达到额度后可能发生节流，所以宿主机有空闲，并不能保证容器继续执行。

查的时候先确认 cgroup 版本和容器实际所属的目录。v1 通常从 cpu.cfs_quota_us 和 cpu.cfs_period_us 读取配额与周期；v2 则从 cpu.max 读取。不要因为找不到 cpu.max，就判断系统没有设置限制。

还要留意父级限制。即使当前这一层没有设置上限，也不能直接推断整个层级都没有限制。配额信息需要沿实际层级核对，不能只看一个文件就下结论。

计数增加了，究竟说明什么

cpu.stat 里的 nr_throttled 可以帮助判断是否发生过节流，但它是累计计数。要解释某一轮压测，应在开始和结束时分别读取，再看这段时间内增加了多少，并与同期的 nr_periods、吞吐和延迟一起比较。

这里最容易混淆的是“发生过多少次”和“总共持续多久”。发生节流的周期占比高，不等于同样比例的请求失败，也不等于每个周期都被完整阻塞。v1 的 throttled_time 使用纳秒，v2 的 throttled_usec 使用微秒，放进同一份记录前要统一单位。累计节流时间也不能直接当作单个请求的等待时间。

为什么原文第一轮数据要作废

原文实验里，服务端监听队列默认是 5，压测并发却是 8。作者发现延迟波动不能简单归因于 CPU 配额，将队列改为 128 后作废旧数据，重新跑了对照。即使结果看起来符合预期，也要确认是不是其他变量造成的。

否则，看到延迟变高就说“CPU 被限速了”，很容易把连接排队、应用处理和配额等待混在一起。能解释某个现象的原因，未必就是当前这组数据证明了的原因。

配额提高以后，还要看业务有没有跟着变

原文后续的对照中，配额从 0.5 核提高到 1 核时收益明显，从 1 核提高到 2 核后收益却很小。这不能推导出其他业务也应该使用相同配置。调整配额后，要同时看节流是否减少，以及吞吐、延迟是否改善。

如果节流减少，业务指标也改善，配额就有了更直接的证据支持。如果节流已经消失，性能仍不动，就应继续检查应用的并行方式、锁等待、I/O 或下游调用。继续加配额，并不能替代这一步判断。

下次遇到类似现象，可以把同一时间段的宿主机使用率、容器配额、实际 CPU 用量、节流差值和请求延迟放在一起看。先确认容器受到了什么限制，再安排可回滚的单变量对照，通常比仅凭整机利用率决定要不要扩容更有依据。
