openGauss 查慢 SQL，先分清执行计划里的估算和实际值

看到一条 SQL 很慢，先给过滤字段加索引，是一种常见反应。但执行计划里值得先确认的是：数据库以为会处理多少行，实际又处理了多少行，以及时间主要花在哪一步。

EXPLAIN 展示预计执行计划，包括访问表的方式和连接等操作。EXPLAIN ANALYZE 则会实际执行语句，并给出相应运行信息。两者不是信息多少的简单区别，后者确实会让工作发生。

因此，分析写入、更新或删除语句时，不能把 EXPLAIN ANALYZE 当作纯查看。即便安排事务回滚，也仍然执行了语句，可能占用资源、持有锁或触发其他行为。选择合适的环境和测试数据，比在业务高峰直接套命令更稳妥。

读计划时，可以沿数据流看扫描、连接、聚合与排序。先找估算行数与实际行数差得较大的位置：如果优化器按少量数据选择了处理方式，实际却得到很多行，后面的工作就可能被放大。这个差异是一条线索，需要继续检查数据分布、条件和统计信息，不能仅凭它认定根因。

计划中的 cost 是估算代价，不应直接按毫秒读。实际时间、返回行数和执行次数也要结合当前版本的字段定义理解。尤其是同一个节点执行多次时，单次看起来不长，累计工作仍可能很大。

看到顺序扫描也不必立即认定没有优化好。表很小，或者查询需要读出较大比例的数据时，顺序读取可能是合理选择。索引是否有帮助，应结合过滤后的数据量、访问方式和实际代价判断，而不是把出现 Index Scan 当作唯一目标。

若计划和预期不同，再考虑统计信息是否反映当前数据、条件是否能有效利用已有索引，以及表达式或类型转换是否改变了访问方式。ANALYZE 用于收集统计信息，与 EXPLAIN ANALYZE 的用途不同，名字相似但不要混为一次操作。

偶发慢查询还需要保留发生时的上下文。事后在低负载下重跑很快，只能说明这次运行快；原来是否等待锁、是否遇到资源争用，仍要看故障时段的记录。单次执行计划不能替代所有运行现场信息。

参考资料：openGauss《EXPLAIN》《SQL 执行计划介绍》及《慢 SQL 问题常见问题与解决方法》。本文为阅读执行计划的思路，未连接数据库或执行任何 SQL。
