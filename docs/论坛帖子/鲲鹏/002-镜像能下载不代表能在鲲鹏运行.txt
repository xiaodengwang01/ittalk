镜像能下载下来，不代表里面的程序能在鲲鹏上运行

容器镜像拉取成功，启动时却报 exec format error，这类问题应该先从实际执行文件的架构查起。仓库可访问、标签存在，只解决了下载问题，还没有回答程序能否在当前机器执行。

先确认宿主机的架构，再查看本地镜像的系统与架构信息。宿主机可以用 uname -m 查看，镜像细节可以用 docker image inspect 检查。鲲鹏环境里常见的 aarch64 与 Docker 平台名称里的 arm64，属于需要对应理解的命名；不要因为字符串不完全一样就认定架构冲突。

镜像标签也不等于架构。同一个标签可能对应多个平台的镜像清单，由运行环境选择合适版本；也可能只提供单个平台。问题定位时，最好记录实际拉取的镜像摘要与平台，而不是只记一个会变化的 latest 标签。

还有一种更隐蔽的情况：基础镜像已经是 arm64，构建时却把原来 x86 环境编译好的程序直接复制进去。容器的基础系统可以启动，轮到那个程序执行才失败。此时继续换基础镜像未必有效，需要检查被复制的可执行文件和原生依赖。

Python 或 Java 项目同样不能只看主语言。Python 的二进制扩展、通过 JNI 加载的本地库，以及启动脚本调用的辅助程序，都可能带有架构要求。纯文本源码可以跨平台，不代表整套依赖已经跨平台。

使用 Docker 的多平台构建时，目标平台参数描述的是希望生成哪种产物。构建过程仍需要通过原生节点、模拟执行或交叉编译来得到相应程序。参数写成 linux/arm64，不会自动把随包带入的 x86 二进制改成 ARM 版本。

模拟环境可以帮助验证流程，但其耗时不能直接当作目标机器的原生性能。迁移确认至少要拆成两步：先验证能正确启动和完成任务，再到实际目标平台测性能。否则，一个“跑通”的结果很容易掩盖执行方式的差别。

如果架构已经对应，仍有同类报错，就继续查实际入口文件、脚本解释器和文件格式，别把所有启动失败都归为芯片架构问题。最有用的记录是宿主平台、镜像平台、失败的具体入口，以及那个文件由哪一步构建得到。

参考资料：Docker《Multi-platform builds》《docker image inspect》及《Dockerfile reference》。本文为迁移检查思路，没有在本机构建或运行鲲鹏容器。
