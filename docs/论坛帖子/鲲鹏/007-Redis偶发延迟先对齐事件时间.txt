鲲鹏上的 Redis 偶发变慢，先把延迟和后台事件对上时间

大多数请求都很快，只有少数时刻延迟突然上升，这种问题只看平均值很容易被略过。排查的第一份记录应该是“什么时候开始慢、持续多久、当时发生了什么”，而不只是一个最高延迟。

先区分客户端等待和命令实际执行。客户端看到的耗时还可能包括网络、排队等环节。Redis 慢日志关注命令执行时间，不能覆盖全部客户端等待；慢日志里没有对应记录，不等于那次延迟不存在。

再把同一时间段的后台事件放到旁边看。持久化相关操作、内存变化、磁盘活动以及系统调度，都可能提供线索。Redis 的延迟监控功能可以记录特定内部事件，但需要确认监控已经启用，并理解所设阈值，否则一份空记录也不能说明从未发生问题。

透明大页是其中一个值得检查的因素。Redis 官方的延迟诊断文档专门讨论了 THP 与 fork 之后写时复制开销的关系，并给出了相关配置建议。它说明一种可能的机制，却不能替代对当前实例的判断：仍要确认实际配置、使用情况，以及延迟是否与对应事件重合。

也不要把普通大页、透明大页和不同架构的基础页大小混在一起。内核文档中的页大小示例有前提，不应直接当作所有鲲鹏系统的固定参数。系统版本不同，THP 的支持与控制方式也可能不同，应按当前内核与 Redis 版本核对。

如果准备调整配置，先保存原状态，在可回滚的实例上观察。记录应同时覆盖相近的请求负载和相关后台操作；只在空闲时测一遍，可能根本没有触发之前的延迟场景。

一次变化若让延迟下降，还要确认其他条件没有一起改变。例如持久化策略、数据规模和客户端位置同时变化，就很难判断是哪项起作用。尤其不应只为了测试数字好看就降低持久化要求，再把结果当作没有代价的优化。

THP 没有解释问题时，就顺着同一个时间窗继续看交换、慢命令、磁盘或网络等线索。保留尚未解释的事件，比每遇到 Redis 抖动都套一份系统参数清单更容易积累有效经验。

参考资料：Redis《Diagnosing latency issues》《Redis latency monitoring》《SLOWLOG》，Linux《Transparent Hugepage Support》。本文为排查资料整理，不包含在鲲鹏实例上测得的延迟或调优收益。
