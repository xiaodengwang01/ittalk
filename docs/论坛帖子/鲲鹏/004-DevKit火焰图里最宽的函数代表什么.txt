看 DevKit 火焰图，先问这张图采的是什么

打开一张火焰图，最宽的函数很容易成为第一个修改目标。但动代码前，最好先确认采样事件。CPU、内存分配、锁等不同事件生成的图，看起来相似，宽度代表的却不是同一种开销。

以 CPU 采样为例，较宽的调用路径表示采样中较多地出现了这条路径，它适合帮助寻找 CPU 时间花在哪里。分配事件的图则围绕分配行为，不能把它的宽度直接读成 CPU 使用比例。DevKit 的热点分析支持不同事件，阅读图之前应把事件类型与采样窗口一起记下来。

通常的聚合火焰图也不是从左到右播放的时间线。横向位置主要用于排布调用路径，不能因为一个函数在左边，就说它先于右边的函数执行。想知道两段工作在时间上如何衔接，需要另看相应的时序数据。

父函数很宽，还要沿调用关系看它调用了什么。父层可能包含子调用的消耗，不宜把每一层的宽度简单相加，也不能只凭父函数名字就认定这段代码本身耗时最多。找到具体路径和调用场景，才更方便回到源码讨论。

另一个容易误判的场景是：请求很慢，CPU 却不忙。只看 CPU 采样，等待锁、等待 I/O 或未获得调度的时间可能没有被完整呈现。这时需要结合线程状态、锁与等待分析等数据，不能因为图里没有很宽的计算函数就宣布“程序没问题”。

采样质量也会限制结论。时间窗过短、选错进程、符号信息不完整，都可能让结果难以解释。尤其是图里大量未知符号或调用关系异常时，应先检查采集与符号解析，而不是围绕一条不可靠的栈展开优化。

真正有用的下一步通常很小：选一条有代表性的热点路径，确认它处理了什么输入、被调用多少次，以及是否存在重复工作。修改以后，在相近负载下再次采样，并比较业务耗时。热点消失但总耗时不变，也是一条需要继续解释的信息。

阅读依据：鲲鹏 DevKit《热点分析》《热点函数分析》、锁与等待分析说明，以及 Brendan Gregg《Flame Graphs》。本文为读图方法整理，没有把示例调用栈当作某个实际应用的诊断结果。
