# Tailki

日常资料统一放在 `KOL搜集与邮件回复/`：

- `达人跟进表.xlsx`：唯一业务表，保留“达人开发主表”和“邮件记录”两张工作表。
- `邮件模板.docx`：拟写首联和后续回复时使用的模板。
- `参考资料/`：回复策略、三位达人回复、公司手册等背景材料。

复用现有文件，不建立重复主表或未使用的空目录。旧表工具只处理本机资料；独立首联入口可以接入 IMAP 核对相关历史和保存草稿。所有入口均不发送邮件，不启用定时任务。

## 首联邮件草稿

用户指定的当前文件为 `KOL搜集与邮件回复/达人跟进表2.xlsx` 和 `KOL搜集与邮件回复/Tailki_KOL初次建联邮件_三个版本.docx`。独立入口 `scripts/mail_drafts.py` 按表头只读，不改名、不改写工作簿或文档；下文旧表更新命令仍只适用于原“达人开发主表、邮件记录”结构，不能用于覆盖当前文件。

五项操作：

- `prepare`：传入 `--book`、`--template`、`--ids`（本批明确达人 ID，以逗号分隔）、`--batch`、`--expect-count`；仅当初次建联日期已确认为计划日期时传 `--planned-date YYYY-MM-DD`。按三类模板填好邮箱、邮箱前缀和 TikTok 账号；缺项、已有回复、共享邮箱等先跳过并报告。
- `setup --gui`：在本机窗口输入完整邮箱和三方客户端安全密码，验证加密 IMAP 连接、识别草稿箱及已发送文件夹，再将专用密码存入 macOS 钥匙串。密码没有命令行参数，不进入日志或 Git。文件夹无法唯一识别时，用 `--drafts-folder`、`--sent-folder` 指定现有文件夹，不创建新文件夹。
- `audit 批次编号`：仅核对本批收件人相关的收件箱、已发送及已有草稿，发现历史或归属问题先跳过；不改变已读状态。
- `save 批次编号`：重新核对源文件与历史后逐封保存，第一封读回一致才处理下一封。没有 SMTP 连接或发送操作。上传结果不明时停止，重跑先核对原草稿，不盲目重传。
- `verify 批次编号`：读回并记录网页修改，已删除、人工发送或无法关联的草稿不自动重建；`--show` 显示完整本地初稿和已读回版本，`--local` 可在未配置邮箱时只查看本机文本。

命令形式为 `python3 scripts/mail_drafts.py 操作 参数`。本批真实 ID、邮箱、正文及运行结果不写入公开说明。程序的单个本机状态库位于 macOS 用户目录 `Library/Application Support/Tailki/mail-drafts.sqlite3`，默认权限为仅当前用户可读写。同一状态库不允许两个任务同时运行；更换邮箱、源文件或名单不会静默覆盖已有批次。

管理员需允许该账号使用第三方客户端及 IMAP 服务，员工在网页端“设置 → 账户与安全 → 账户安全”生成专用安全密码。连接地址为 `imap.qiye.aliyun.com:993`，强制校验证书。参见[官方配置](https://help.aliyun.com/zh/document_detail/36576.html)和[安全密码设置](https://help.aliyun.com/zh/document_detail/444269.html)。

在邮箱草稿箱逐封审核和修改后，回到对话明确确认具体批次。SMTP 发送不在当前入口中，后续须读取最终稿、展示完整内容并单独取得批次发送确认；准备草稿或保存凭据不构成发送授权。

模拟检查：`python3 -m unittest scripts.test_mail_drafts -v`。测试只用 `SIM-` 编号和 `.invalid` 邮箱，覆盖分类、占位符、名单筛选、历史核对、重复运行、上传中断、网页编辑、删除和人工发送后的保护。

## 两张表的用途

主表一行对应一个平台账号，`达人ID`生成后不随排序改变。日常先看“沟通摘要、联系状态、下一步动作、计划跟进日期”。沟通摘要记录对方要求、已知合作条件和未解决问题；寄样、物流和发布字段继续折叠。

按平台和规范账号链接去重，不按经纪人邮箱合并达人。邮箱列只存单一邮箱，联系页另存。粉丝数和播放量存数字；来源链接、抓取时间及核实说明用于追溯。旧表联系日期和缺少年份的截图时间不当作已核实的发信事件。

邮件记录一行对应一封收信或一封**实际发送的后续回复**。初次建联正文、未发送草稿和图片不进入邮件记录。原有 3 封未发送草稿已移出邮件记录，`参考资料/三位达人回复.docx`保持不变。只有发信引用头、没有本封回复正文的旧记录不作为已发送回复，必要说明保留在主表。

按用户要求保留的当前草稿放在主表右侧折叠的“草稿状态、草稿收件人、草稿主题、当前回复草稿、草稿来源”列，明确标为“未发送草稿”。这里只留本次新增正文的纯文本，图片不保存；草稿不更新最近发信时间、我方实际报价或已发邮件历史。发送后核对实际文本再归档，并清除主表当前草稿字段。当前草稿改变时，相关沟通摘要会标为待更新。

邮件表默认展示达人、收发方向、时间、主题、邮件摘要、处理状态和正文完整性。完整正文、联系方式、来源及核实说明折叠，技术字段另设一层折叠；表头和身份列冻结，行高保持紧凑。展开正文列后选中单元格，可在编辑栏读取全文，需要时手动调整行高。

`邮件正文`只存本封新增内容，保留原话和段落，去掉明确重复引用的旧邮件链。摘要单独保存，不能替代正文。`记录来源`区分截图转录与原邮件文本；`正文完整性`使用“完整、部分、待核实、缺失”。截图裁切、无法辨认或缺失的内容以标记和核实说明保留，不补写成原文。归属不明确的邮件继续标为“待人工归属”。

明确标记的旧引用会移除，行内或底部的新回复会保留；无法区分旧邮件与新增正文时停止导入或补全，先人工核实，不猜测删去原文。

## 按达人读取

折叠方便人工浏览，**不会自动减少 AI 读取的上下文**。以下两个只读入口明确控制返回范围，不改写工作簿：

```bash
python3 scripts/workflow.py overview
python3 scripts/workflow.py context KOL-000001
```

`overview`返回达人进展摘要和邮件索引，不返回完整正文、联系方式或来源说明。`context <达人ID>`返回该达人的全部归档收信和已发送后续回复正文，不读取其他达人全文，也不包含未归属邮件、首联或草稿。

时间明确的邮件按时间排列；时间不明的邮件另列，保持原记录顺序，不推测先后。默认每页预算为 24000 个字符，可用 `--budget 12000`调整。分页以完整邮件为单位，结果会说明本页范围、总封数、是否读完和“下一页游标”。单封邮件超过预算时仍完整返回，并明确标记，不静默截断或改成摘要。

有下一页时，将输出的“下一页游标”完整 JSON 传入 `--cursor`。例如下列游标结构中的位置和快照须使用实际返回值：

```bash
python3 scripts/workflow.py context KOL-000001 --budget 12000 --cursor '{"达人ID":"KOL-000001","位置":2,"快照":"实际返回的快照值"}'
```

游标绑定达人和邮件快照；邮件变化后旧游标会被拒绝，需要重新从第一页读取。不要仅凭已读摘要判断已读完往来。

## 本地更新

使用 Python 3.9 或更高版本，以及 Codex 自带的 Node 和表格工具，无需安装项目依赖。可用 `TAILKI_NODE`和`TAILKI_ARTIFACT_MODULES`指定运行环境。每次写入先在本机临时目录生成，核对字段和备注后替换原文件；处理中若原文件变化则停止覆盖。

```bash
python3 scripts/workflow.py check
python3 scripts/workflow.py refresh
python3 scripts/workflow.py import-scrape /本机路径/抓取结果.json
python3 scripts/workflow.py import-mail /本机路径/邮件结果.json
```

默认操作日常目录中的原表；模拟检查可在子命令前加 `--book /本机路径/模拟.xlsx`。`--preview`会在本机临时目录生成预览，不在业务目录增加文件。`refresh`只更新进展、下一步动作、日期和摘要有效性，保留用户要求保存的主表当前草稿，不自动生成草稿，也不会向邮件记录写入草稿、首联正文或图片。

抓取输入为记录数组或以下结构。只有提供真实抓取时间和来源链接时才更新抓取时间；与已有邮箱或人工分类冲突时保留原值并提示核实。

```json
{
  "抓取时间": "2026-10-19T10:00:00+08:00",
  "creators": [{
    "平台": "TikTok",
    "账号链接": "https://www.tiktok.com/@sim_alpha",
    "达人昵称": "模拟达人 Alpha",
    "Email": "alpha@example.invalid",
    "首联内容分类": "宠物剧情类",
    "粉丝数": "8.5m",
    "来源链接": "https://www.tiktok.com/@sim_alpha"
  }]
}
```

邮件输入为记录数组、单条记录或 `{"messages": [...]}`，使用表头同名字段。收信示例：

```json
{
  "方向": "收信",
  "达人ID": "KOL-000001",
  "邮件时间": "2026-10-19T10:00:00+08:00",
  "邮件原始时间": "2026-10-19 10:00 +08:00",
  "发件人": "alpha@example.invalid",
  "收件人": "team@example.invalid",
  "主题": "Re: 示例合作",
  "邮件正文": "Thanks for reaching out.\n\nCould you share the product details?",
  "正文完整性": "完整",
  "记录来源": "原邮件文本导入",
  "邮箱消息ID": "sim-message-001",
  "邮箱账户": "team@example.invalid"
}
```

邮件原生消息 ID 优先用于去重，并按邮箱账户区分。`原邮件定位`应精确到单封邮件，会话链接不能替代单封标识。无唯一标识且缺少完整时间、双方地址、主题或正文时，不贸然判作重复。共享邮箱和账号归属冲突留待人工处理：

```bash
python3 scripts/workflow.py assign-mail MAIL-000001 KOL-000001
```

归档实际发送的后续回复时，必须有本封正文，并注明`方向=发信`、`邮件用途=回复`、`实际发送结果=成功`，可用`回复邮件记录ID`关联所回复的来信。发送确认批次等字段只记录已有事实，不构成发送授权。

初次建联只可导入已观察到的发送元信息：明确的达人 ID、`方向=发信`、`邮件用途=首联`、`实际发送结果=成功`以及完整实际发送时间。程序只更新主表的首次联系日期、最近发信时间等信息，不归档首联主题或正文。时间仅有年月日时保留原精度，不补出时分；完整邮件时间按北京时间入表，原始时间另存。

已核实成功发送的首联，第 7 个工作日仍无收信时，`refresh`将下一步动作标为“跟进草稿”；工作日先按周一至周五计算。收到回复后停止催复；暂停联系、邮箱缺失、历史发送未核实或发送结果未知时不触发催复。草稿仍在对话中拟写和审核。

## 补全文本和更新摘要

重复导入同一邮件不重复建行，也不自动覆盖不同正文。补全部分转录时，明确指定原邮件记录 ID：

```bash
python3 scripts/workflow.py fill-mail MAIL-000001 /本机路径/补全文本.json
```

补全文件可包含`邮件正文、正文完整性、记录来源、原邮件定位、核实说明`等字段；未提供的字段保留原值，邮件 ID 和达人归属不能改变。已有完整原文与候选正文冲突时保留原文并提示核实，不把候选正文混入摘要或备注。

新来信、正文补全、更正或相关元信息变化后，程序会将受影响的摘要标记为“待更新”。这只是检测摘要依据变化，**不会自动生成新的语义摘要**。阅读相关全文并核实后，通过以下入口更新邮件摘要和达人沟通摘要：

```bash
python3 scripts/workflow.py update-summaries /本机路径/摘要更新.json
```

输入按现有 ID 对应摘要文本，可只更新其中一部分：

```json
{
  "messages": {"MAIL-000001": "对方请求产品资料，尚未提供报价。"},
  "creators": {"KOL-000001": "对方希望先了解产品；合作费用和交付内容待确认。"}
}
```

更新后记录摘要依据指纹及“有效”状态；后续变化仍会再次标记过期。`convert-text --annotations /本机路径/核实转录.json`仅用于已有截图表的明确转录迁移，日常刷新不需要重复执行。

## 发送、检查与 Git

发送仍须在对话中展示对应批次的收件人、主题和完整正文，取得用户明确确认后，才通过已授权的邮箱网页执行。收件人、主题或正文改变后须重新确认；发送结果不明时先核实，不自动重发。未发送草稿不进入邮件历史，发送后再归档实际文本。本地程序不连接邮箱，也不代替发送确认。

```bash
python3 -m unittest scripts.test_workflow_rules scripts.test_mail_text scripts.test_workflow_adapter -v
```

自动检查使用模拟数据，覆盖归属与去重、草稿和首联排除、正文补全冲突、摘要过期、按达人分页，以及表格保存与折叠。旧的 `scripts/examples/Tailki_模拟.xlsx`仍是三页上传安全示例，不替代两页业务表。

真实名单、邮箱内容、登录资料和运行记录全部留在本机。Git 只上传程序、说明和模拟示例，不上传业务目录，也不改变其忽略规则。

每次修改并检查后，由 Codex 运行 `python3 scripts/git_sync.py "修改说明"`提交并上传；不强制推送，上传失败保留本地提交。也可使用“一键上传.command”。首次 Token 授权使用“首次授权并上传.command”，只在本机安全输入框填写，凭据保存到 macOS 钥匙串。
